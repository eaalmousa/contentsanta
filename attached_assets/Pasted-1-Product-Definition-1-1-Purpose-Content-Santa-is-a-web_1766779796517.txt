1) Product Definition
1.1 Purpose

Content Santa is a web platform that:

ingests raw content (links, drafts, briefs, transcripts, notes)

enhances it using specialized AI workflows (rewrite, expand, translate, SEO, social variants, visuals prompts, compliance checks)

produces ready-to-publish assets

optionally publishes/schedules to connected channels

maintains a searchable content library with brand voice, templates, and approvals

1.2 Target Users

Agencies (small/mid), marketing teams

Founder-led businesses

Content editors and social teams

Solo creators operating multiple brands

1.3 Core Outcomes

Faster production of higher-quality multi-format content

Consistent brand voice

Fewer approval cycles

Measurable output (assets produced, time saved, publishing performance)

3) Architecture on Replit
3.1 Recommended Stack (Replit-friendly)

Frontend

React + Vite (or Next.js if you prefer, but Vite is simpler on Replit)

TailwindCSS

TipTap (rich editor) or simple Markdown editor (MVP)

Backend

Node.js + Express (simple, stable on Replit)

PostgreSQL (Neon or Supabase Postgres) recommended over Replit DB for relational requirements

If you insist on Replit Database: it works, but you’ll rebuild relational guarantees manually. For this product, Postgres is a better foundation.

Storage

S3-compatible object storage (Cloudflare R2 / AWS S3) for files

CDN optional later

AI Orchestration

OpenAI Agent Builder as the workflow orchestrator

Your backend calls:

runWorkflow(workflowType, inputId, brandId, options)

stores outputs and traces

Queues / Jobs

MVP: in-process job runner + DB job table

Phase 2: Redis queue (Upstash) or a lightweight worker

3.2 High-Level Flow

User uploads/creates input

System stores input + metadata

User runs a workflow

Backend calls Agent Builder (or a workflow runner service)

Output saved as asset versions

Review/approve

Export or publish

Analytics updates

7) Agent Builder Orchestration (Replacing n8n)
7.1 Orchestrator Principles

A single entrypoint in backend: POST /workflow-runs

Backend passes:

cleaned input text

brand rules

selected template

workflow config

Orchestrator returns:

structured JSON output

trace

flags

7.2 Implementation Pattern

Backend modules

workflowRunner.ts

validates input + permissions

loads brand rules + template

calls agent

stores run + output draft

Agent responsibilities

chooses the right sub-steps

enforces brand voice constraints

produces structured output JSON

7.3 Prompt Governance

Store prompt versions in DB:

prompt_versions table (optional but recommended)

each workflow references a prompt version ID

allows rollback and audit

8) File Handling: PDF/DOCX/Text Extraction

MVP approach:

DOCX: mammoth

PDF: pdf-parse (best-effort; complex PDFs later)

Store original file in object storage + extracted text in inputs.raw_text

13) Deliverable Standards (Output Quality)

Every generated output must be:

structured, reusable, and editable

tagged with language + channel

compliant with brand rules

flagged where claims appear unverifiable

saved with full traceability (who ran it, when, and with what configuration)

14) Acceptance Criteria (MVP)

MVP is considered complete when:

A user can create a workspace + brand

Add an input (text/url/pdf/docx)

Run at least 5 workflows

Receive outputs as versioned assets

Edit, comment, approve

Export to DOCX/PDF/Markdown

Usage tracking increments correctly

No cross-workspace data leakage is possible
