Content Santa Automation Pipeline v1.0 — Implementation Spec
0) Objective

Transform Content Santa from a manual, editor-led workflow into an automation-first pipeline where the user only:

Creates a Topic Pipeline (topic + region + rules + schedule)

Connects a Target (WordPress/blog)

Then the system automatically fetches, matches, generates, publishes, and verifies posts.
Any exceptions route to Quarantine with actionable reasons and one-click retry after fixes.

1) Product Rules
1.1 Default mode

AUTO mode is the default for all new topics.

Manual actions (Create Draft / Approve / Publish) are not part of the default path.

1.2 Single source of truth

There must be one canonical publish queue and one canonical status model.

Remove duplicate “Ready to Publish” implementations. The canonical view becomes Topic Pipeline → Approved/Scheduled/Publishing.

1.3 “Published” must mean published on the real target

Hard rule: An item is not “Published” unless:

the target returns target_post_id and permalink, and

the system stores them, and

(recommended) a follow-up GET confirms it exists.

If publish fails, the item remains NOT published and goes to Retrying then Quarantine.

2) Information Architecture (Navigation)

Replace the current fragmented UX with:

Dashboard

3) Core Entities
3.1 Target (WordPress/blog)

A configured destination with auth, taxonomy mapping, and health checks.

3.2 Pipeline (Topic)

The orchestrator: region, language, rules, schedule, caps, target selection, output style.

3.3 Pipeline Item

A story matched to a pipeline, turned into an automated article, then published/verified.

4) Status Model (State Machine)

Implement a single enum for pipeline_items.status:

FETCHED

MATCHED

DEDUPED

RANKED

GENERATED

GATED

SCHEDULED

PUBLISHING

PUBLISHED (target responded successfully)

VERIFIED (target post confirmed)

RETRYING

QUARANTINED

SKIPPED (daily cap/quiet hours/off-topic/etc.)

Transitions

Normal: FETCHED → MATCHED → DEDUPED → RANKED → GENERATED → GATED → SCHEDULED → PUBLISHING → PUBLISHED → VERIFIED

Failure: any step → RETRYING (bounded) → QUARANTINED

Policy/cap: GATED → SKIPPED or SCHEDULED → SKIPPED

6) Background Jobs (Automation Engine)

You need a job runner (cron + queue). Implement as:

Node cron + DB polling, or

a simple queue table + worker, or

your existing infra.

6.1 Job cadence

For each live pipeline:

Run Fetch → Match/Rank → Generate/Gate → Schedule → Publish → Verify as a chain.

Jobs can be separate functions but must be observable.

6.2 Jobs (definitions)
A) FetchJob(pipeline_id)

Pull new stories from sources relevant to pipeline’s source_mode.

Store in stories (existing).

Mark as FETCHED pipeline_items if you do direct item creation here, or defer to MatchJob.

Output:

Create/identify candidate stories since last run.

B) MatchAndRankJob(pipeline_id)

Select recent stories not yet associated to pipeline.

Apply:

region relevance (if supported)

include/exclude keywords

language pre-check (quick)

Create pipeline_items with MATCHED.

Compute dedupe_hash, run dedupe:

If duplicate of already PUBLISHED/VERIFIED, set SKIPPED with reason “duplicate”

Else proceed DEDUPED

Score & rank; update score, set RANKED.

C) GenerateJob(pipeline_id)

Take top N ranked items not generated.

Generate article content using pipeline output_settings.

Save generated_title/body/excerpt/tags/category.

Set status GENERATED.

D) QualityGateJob(pipeline_id)

Automated checks:

language detection (strict): if pipeline language=en and detected not English → QUARANTINED reason LANGUAGE_MISMATCH

off-topic threshold (score below threshold) → SKIPPED reason LOW_RELEVANCE

policy flags (politics/conflict) → QUARANTINED reason POLICY_BLOCK

missing fields → QUARANTINED reason INVALID_CONTENT
If passes → GATED

E) ScheduleJob(pipeline_id)

Apply:

daily cap

min spacing between published posts

quiet hours
Assign scheduled_for and set SCHEDULED.
If cap reached or quiet hours → SKIPPED reason CAP/QUIET_HOURS or schedule for next window.

F) PublishJob(pipeline_id)

Select items where:

status=SCHEDULED

scheduled_for <= now
Set PUBLISHING, increment attempts.
Call target publish API.
On success:

store target_post_id, target_permalink, wp_status

set PUBLISHED, set published_at
On failure:

set RETRYING, store error (status code, payload)

Important: Do not set published internally unless API returns success.

G) VerifyJob(pipeline_id)

For PUBLISHED items:

GET by target_post_id (or fetch permalink).
If exists:

set VERIFIED, set verified_at
If not:

RETRYING then QUARANTINED reason VERIFY_FAILED

6.3 Retry policy

retry_count < 5

Backoff schedule: 1 min, 5 min, 20 min, 60 min, 6 hours

After max retries → QUARANTINED with reason and suggested fix

7) WordPress Publishing Contract (Target Adapter)
7.1 Endpoint

Create post: POST {base_url}/wp-json/wp/v2/posts

Verify post: GET {base_url}/wp-json/wp/v2/posts/{id}

7.2 Auth

Use Application Passwords: Basic Auth with wp_username:wp_app_password

Ensure you store only encrypted secret.

7.3 Payload

Minimum:

title (generated_title)

content (generated_body)

excerpt (generated_excerpt)

status = publish (default)

Optional:

categories and tags IDs (requires mapping sync)

featured image upload then set featured_media

7.4 Taxonomy sync

In Targets screen:

“Sync Categories/Tags” button

Pull WP taxonomies and store mapping locally

If mapping missing at publish time:

either publish without category (safe default), OR quarantine with TAXONOMY_MAPPING_MISSING depending on strictness setting.

Recommended default: publish without taxonomy if missing; log warning; do not fail.

10) Migration Plan
Phase 1 — Status unification

Introduce pipeline_items and canonical status enum.

Map existing Draft/Approved/Published records into pipeline_items where possible.

Phase 2 — UI restructure

Add new navigation + Pipeline screens.

Convert Smart Editor into Quarantine-only.

Phase 3 — Job runner

Implement job chain with job_runs logging.

Ensure pipeline runs automatically when is_live=true.

Phase 4 — Remove duplicates

Remove/disable old “Ready to Publish” lists that conflict.

Ensure only pipeline screens show publish queue.

11) Acceptance Criteria (Sanity Check)

A pipeline is considered “logical, working, automated” only if:

Auto publish without manual clicks

Create pipeline + connect target + turn on

System publishes at least 1 post automatically on next run

Published = real

Every item marked VERIFIED has:

target_post_id + target_permalink

WordPress shows the post

Failures are visible and honest

If WP publish fails:

item is NOT published internally

item is set to RETRYING then QUARANTINED

quarantine shows exact error + retry button

Topic drives content

Pipeline queues show only matched items for that pipeline

Language mismatch goes to quarantine

Observability exists

Logs show job runs and publish attempts with clear outcomes

12) Default Settings (Recommended)

daily_cap = 5

min_spacing_minutes = 120

quiet_hours = 22:00–07:00 Asia/Dubai

taxonomy_strict = false (publish without taxonomy if missing)

max_retries = 5
